# Verification status

For the system claims and how the checked evidence composes, start with the [proof architecture](proof-architecture.md). This inventory gives the component and experiment proof scopes.

## Storage engine guarantees

The current engine is the sequential Linux `DiskTable` API. Lean checks its table, codecs and shared storage protocol against a logical key-value store and a model of the files that survive a crash. The engine uses v3 run files and v2 checkpoint manifests. These version numbers identify different artifacts. The v1 packed blocks and Verus search core are separate experiments. [Engine and I/O protocol](architecture.md#sequential-storage) · [Packed experiments](#packed-block-and-search-experiments)

- **Durability.** Every acknowledged write survives in order across the crash and recovery sequences admitted by the mixed segmented trace. The selected marker retains all or none of an uncertain batch. [Mixed trace](../lean/Alvoki/Storage/Disk/SegmentedBatchDatabaseTrace.lean)
- **Read correctness.** The session returned by marked reopen agrees with abstract replay for point and ordered range reads at supported snapshots. An unsupported request leaves that session unchanged. Previous live snapshot tokens remain foreign under the reported token comparison. One final WAL replay explains each successful recorded read at its original active local pin, even if the retention floor later passes that snapshot. The recorded session and pin checks explain denied reads. [Reads from the returned session](../lean/Alvoki/Storage/Disk/CachedRetrySnapshotReads.lean) · [Recorded client reads](../lean/Alvoki/Storage/Disk/ClientReadTrace.lean)
- **Exact recovery.** The admitted opener uses the surviving manifest, its exact run files and the retained WAL to determine the recovered table, generation and active WAL segment. Around the last checkpoint directory sync, either the previous selection or the new manifest can survive before the reported effect. After the effect, only the new manifest survives. A returned staging, rename or final directory sync error extends the client trace through the admitted reopen with the same submissions and recorded reads. [Final checkpoint barrier](../lean/Alvoki/Storage/Disk/CheckpointManifestDirectoryCut.lean) · [Client trace after a staging error](../lean/Alvoki/Storage/Disk/ClientReadTrace.lean#L313) · [Client trace after rename or directory sync errors](../lean/Alvoki/Storage/Disk/CheckpointManifestErrorClientTrace.lean)
- **Native boundary.** An observed descriptor history carries the held lock and directory cache through the checked listing and first sync. It connects the selected checkpoint run reads to the same directory. The proof uses explicit reports for raw identity, file contents, namespace changes and durability. Native fault tests exercise specific Linux outcomes. [Directory custody](../lean/Alvoki/Storage/Disk/HeldDirectoryReadObservations.lean) · [First directory sync](../lean/Alvoki/Storage/Disk/ListedDirectoryAuthorization.lean) · [Proof roadmap](proof-roadmap.md#end-to-end-storage-guarantees)

### Durable batches

The batch API shares the append and marker publication schedule, with one append, two file barriers before rename and a directory barrier after rename. Lean relates preparation to sequential replay and connects reached I/O callback reports to the exact committed or failed file state. The mixed trace covers reported batch errors, machine power loss and observed process exit during append and marker publication. It preserves acknowledgements in order and retains an uncertain batch in full or discards it in full. Acquiring a supported snapshot records its pin in the same ready session before the guarded point or range read, which agrees with replay given the reported token comparison. Native fixtures exercise the publication and lock cuts. The proofs assume truthful primitive reports for durable prefixes, effects, reads, repair and lock ownership. [Native schedule](../lean/Alvoki/Storage/Disk/DiskTable.lean) · [Reported failures](../lean/Alvoki/Storage/Disk/WalBatchSession.lean) · [Mixed trace](../lean/Alvoki/Storage/Disk/SegmentedBatchDatabaseTrace.lean)

The healthy aligned repair follows the exact keeper descriptor through the two reported barriers. If the keeper sync fails after the first barrier, the reached image always includes directory settlement and applies the keeper's file-sync effect when the report says it took effect. The admitted opener performs local lock cleanup, and the retry starts from the returned image and owner. With a successful stage write and no visible later WAL files, the long-keeper proof also follows the staged inode through rename and the last directory barrier to the installed session. [Aligned repair](../lean/Alvoki/Storage/Disk/ListedAlignedKeeperRepair.lean) · [Aligned repair failure](../lean/Alvoki/Storage/Disk/ListedAlignedKeeperFailure.lean) · [Staged replacement](../lean/Alvoki/Storage/Disk/ListedStagedKeeperRepair.lean)

After a completed run-retention pass, checkpoint with empty pending memory and both collectors, the named payload is the rewritten runs, extra surviving run names and the active WAL payload. Explicit budgets for the extra run bytes and active WAL width give a total namespace payload bound. Complete inventories, stable holds, successful maintenance and its scheduling remain required. The bound covers bytes at names. Filesystem allocation and references to unlinked inodes have separate obligations. [Named maintenance budget](../lean/Alvoki/Storage/Disk/NamedMaintenanceBudget.lean)

The selected WAL decoder performs at most one format check and one ordinal check per complete retained frame through the marker. The replay fold attempts at most one write per frame above the checkpoint watermark. Both counts reach their bounds on successful recovery. The proof charges the first failed attempt and excludes later work in that stage. These are source-operation bounds. ## Optimized reader and search

`lean/OptProofs.lean` proves that the tail-recursive machine-index search agrees with the original natural-number lower bound after index conversion. It derives the same partition guarantee for monotone logical keys. `wordMachine_eq` proves the optimized reader is equal to the original byte reader when the eight-byte extent is in bounds and the array size fits in a machine word. Each proof-carrying byte load and indexed store uses an explicit bound, and Lean checks the progress of the machine-index loops.

The parser acceptance proof certifies input bytes, header count and version, layout, and strict order at logical offsets. Checked record access agrees with those offsets, and the optimized lower bound partitions the keys of accepted blocks. The v1 run API checks natural-number indices before converting them to machine width. Scalar kernel access checks the record bound and returns zero at exhaustion. For every strictly ordered array within the format and machine bounds, `encodeV1` followed by `parseRun` and `Run.decodeV1` recovers the exact array. Decoding and re-encoding an accepted block reproduces its bytes. The baseline, scalar and indexed encoders are equivalent to `encodeV1`. The materializing decoders and the streaming checksum refine the same decoded rows.
