# High-performance Lean for packed storage

Alvoki compares native Lean 4.36.0 and Rust 1.100.0 on immutable sorted blocks of 64-bit key–value pairs. Stock Lean reached roughly the speed of the matched Rust routines for many packed reads, including a compiler-vectorized scan. The hardest cases still create new output one record or one word at a time. The practical starting point is to keep data packed, run scalar loops over borrowed buffers, and make copies as large as the workload permits. [Optimization results](../experiments/optimizations.md) · [Native scans](../experiments/native-experiments.md) · [Stock builder results](../experiments/stock-builder.md)

The measurements below are from individual x86-64 VM experiments. Compare a row with its control from the same run. The reports retain workloads, build settings, raw trials, and code-generation evidence where collected.

## Choose the representation and result first

| Technique | When to use it | What we measured |
|---|---|---|
| Keep an immutable packed `ByteArray` and borrow it with `@&` | A caller can keep the backing bytes and needs lookup, a scan, or a packed result | Packed lookup at one million records took 3.32 ms for the Lean query batch and 3.53 ms for Rust. Copying the packed bytes and scanning took 1.78 and 1.11 ms. [Packed experiments](../experiments/packed-experiments.md) |
| Decode records only as the consumer uses them | A reduction or a single traversal can consume key and value as scalars | Streaming decode and fold took 0.919 ms in Lean and 0.873 ms in Rust. Owning decoded records through the fold took 9.97 and 1.19 ms. [Optimization results](../experiments/optimizations.md) |
| Give owned records scalar fields when callers need individual objects | Individual records must outlive the loop or travel through object-oriented APIs | Switching from boxed pairs reduced Lean decode-and-fold from 38.17 to 23.56 ms before read specialization, and peak RSS from 101 to 68 MiB. Generated Lean code still allocated one object per record. Rust's `Vec<(u64, u64)>` stores the fields inline in its backing buffer. [Optimization results](../experiments/optimizations.md) |
| Separate key and value columns when access is key-heavy | A workload spends most probes on comparisons and reads values only for hits or consumption | At one million records, going from interleaved to columnar reduced mixed lookup from 173 to 157 ns in Lean and 182 to 162 ns in Rust. Lean sequential lookup was about 47 ns in both layouts. [Layout sweep](../experiments/optimizations.md) |
| Fuse the merge with a downstream fold when that fold is the whole result | A consumer needs one pass over the merged values and can keep both input runs live | Alternating inputs took 2.09 ms for the direct Lean scan versus 8.91 ms for the best materialized Lean scan, including output validation. Shuffled inputs took 6.17 versus 13.69 ms. Clustered inputs favored materialization slightly, 2.00 versus 2.17 ms, with bulk copies followed by SIMD. For the first three profiles in the report, Lean peak RSS fell from about 40 to 24 MiB. [Direct scans](../experiments/fused-merge.md#direct-merged-scans) |

An owned packed buffer gives callers a reusable representation with a single contiguous payload. A direct fold yields its accumulator and requires a separate path when a caller needs durable merged bytes or later indexed reads. Building a 4 KiB chunked representation added work in the tested build-and-scan case. Prebuilt chunks also scanned more slowly than a contiguous Lean buffer in the same report. ## Make hot reads easy to compile

1. **Validate at the boundary and reuse the result.** Check header, count, length, version and sortedness when constructing a view. Prove the loop's byte accesses from its extent and cursor invariant where possible. In a validation loop, carry the previous key and load each new key once. This reduced legacy validation from 15.66 to 12.88 ms. With machine-sized offsets, wide-load recognition, and the scalar loop together, it reached 0.447 ms. [Parser and validation code](../../lean/Alvoki/Codec/PackedView.lean#L153) · [Optimization results](../experiments/optimizations.md)
2. **Use `USize` for machine indices and `UInt64` for data and wrapping accumulators.** Keep the loop state scalar and conversions at boundaries where feasible. Express the specification and termination measure over `Nat` and prove that valid updates and offset calculations stay in range. A terminating tail-recursive loop yielded a tighter search kernel than the imperative experiment, which lowered to managed loop state. Verify this in the generated code for the function you care about. [Search code](../../lean/Alvoki/Codec/PackedView.lean#L329) · [Refinement proofs](../../lean/Alvoki/Kernel/PackedSearchContracts.lean) · [Optimization results](../experiments/optimizations.md)
3. **Expose fixed-width accesses.** Use one extent guard, proof-carrying `ByteArray.uget` reads, and explicit constant byte offsets with little-endian shifts and ORs. With the bound established, Clang recognized the eight-byte pattern as a single unaligned 64-bit load on x86-64. Check the byte order and offset extent in source as well as the native result. [Word reader](../../lean/Alvoki/Codec/PackedView.lean#L12) · [Optimization results](../experiments/optimizations.md)
4. **Specialize across the hot call path.** Inline small accessors, use `@[specialize]` for a known search callback, and keep closures, boxed pairs and managed loop state out of the inner loop when they survive compilation. The generic mixed lookup took 500 ns. Specializing the comparator with `Nat` indices took 368 ns, and combining specialization, machine arithmetic, and the optimized reader reached 173 ns. Read values only when lookup or consumption needs them. [Search code](../../lean/Optimizations.lean#L162) · [Optimization results](../experiments/optimizations.md)
5. **Use a fixed-stride loop with a simple reduction to give Clang a chance to vectorize.** Borrow the input, establish the full extent outside the loop, keep per-record extent branches out of the body, and use simple scalar state with an explicit tail where the loop needs it. Check compiler remarks and actual assembly at the pinned target. The stock Lean scan took 0.220 ms, the earlier guarded scan 0.868 ms, and Rust took 0.237 ms with vectorization and 0.336 ms with it disabled. Manually unrolling into four accumulators took 0.287 ms and stayed scalar. Auto-vectorization depends on the loop, optimizer, and target. [Scan code](../../lean/NativeTune.lean#L1) · [SIMD report](../experiments/native-experiments.md#simd-scan) · [Disassembly](../../benchmarks/results/packed/native-codegen.txt)

## Write and merge in spans

1. **Copy unchanged packed data in bulk.** A whole payload can be copied when keys from the two runs are disjoint. Long winning stretches can use one copy per span, with a bias toward the per-record path until the same side wins several times. Eager probes hurt alternating and short-span input. The adaptive path was competitive with the Rust per-record control for mixed spans at 2.63 versus 2.68 ms, while perfect alternation still favored Rust at 7.71 versus 1.95 ms using the simple Lean writer. Cache the losing head where it helps and measure the effect separately. [Disjoint fast path](../../lean/Alvoki/Codec/PackedRun.lean) · [Span and cache results](../experiments/emission-experiments.md#merge)
2. **Emit spans as they are found.** A precomputed plan helps when it already exists and has long spans. On clustered replay, Lean took 0.76 ms to write from a plan and 9.73 ms to prepare and write. Online coalescing took 1.55 ms, and the Rust per-record control took 1.19 ms. For a one-shot merge, fuse selection with emission and skip the intermediate trace and array of span descriptors. The bounded-window variant improved clustered merge from 1.23 to 1.07 ms. Its clustered merge–validate–scan–lookup pipeline took 6.21 ms versus 5.70 ms for the prior adaptive variant. Measure both scopes before changing the default. [Replay results](../experiments/stock-builder.md#performance) · [Fused merge results](../experiments/fused-merge.md#fused-span-emission)
3. **Copy once and patch only the bytes known to change.** For a packed transform that flipped one bit per value, the Lean copy-and-byte-patch path took 1.20 ms and Rust took 1.01 ms. Patching all eight value bytes took 4.93 ms in Lean against the same 1.01 ms Rust control. Check the transform's semantics before narrowing its writes. [Packed transforms](../experiments/emission-experiments.md#fresh-packed-output)
4. **Share bounds checks and size allocations for the workload.** Unrolling byte appends improved the first encoder from 59.12 to 31.36 ms. Later indexed stores into a pre-sized output helped the scalar-array encode workload. In the packed transform, checking extent per record instead of per word reduced 10.75 to 7.78 ms. A 4 KiB staging buffer took 15.59 ms because byte stores still happened before the bulk copy. Pre-sizing and overwriting did not accelerate the alternating merge in the tested variant. [Baseline encode](benchmarks.md) · [Indexed encode](../experiments/optimizations.md) · [Staging and extent checks](../experiments/native-experiments.md#fresh-encoding) · [Pre-sized merge](../experiments/emission-experiments.md#merge)
5. **Measure branch behavior by key distribution.** The stock Lean direct scan variant that selected a source using comparisons was slower than the simple branching scan in all four profiles. In the separate scoped C replay prototype, the branchless kernel helped shuffled winners, 4.43 to 1.08 ms, and lost on perfect alternation, 0.87 to 1.05 ms. Inspect the actual branches and conditional moves and keep predictable and shuffled cases in the same suite. [Stock direct scan](../experiments/fused-merge.md#direct-merged-scans) · [Scoped replay](../experiments/scoped-builder.md#what-changed)

## Understand the remaining write cost

A proved `ScopedBytes.Slice` carries an extent, and an append-only `Builder` gives an exact source-level byte contract. `@&` borrows input and a proof in `Prop` erases. Stock `ByteArray.copySlice` still goes through a runtime entry point for each emitted record or span, with dynamic handling for ownership, capacity, offsets, and length. A capacity hint and a private field establish neither a linear API nor a compiler guarantee of unique storage. The generated byte-writer slow-path call sites describe possible fallbacks. Determining how often those fallbacks execute requires runtime evidence. [Builder code](../../lean/Alvoki/Kernel/ScopedBytes.lean) · [Builder proof audit](../experiments/stock-builder.md) · [Writer disassembly](../../benchmarks/results/packed/emission-codegen.txt)

Use `ByteArray.markLinear` and `LEAN_ABORT_ON_NONLINEAR=1` in a diagnostic build to check for copies caused by shared ownership. The marked destinations completed 75 exact cases across v1 replay, v3 compaction, and dense rewrite without a copy-on-write panic. A deliberately retained alias triggered the check for both overwrite and growth. Unique growth succeeded. The results cover the tested paths after marking. Capacity growth, record copying, and the dynamic checks themselves still have their own costs. [Diagnostic and exact cases](../../benchmarks/results/packed/linearity)

We held the input trace fixed to separate emission from selection. At one million total input records, online selection plus checksum was within 18% of Rust across all three profiles. Replay writes were about 4.2–4.6× slower. Replay, selection, and end-to-end merge each have distinct memory traffic and tail handling, so use the phase timings to locate work and measure the full pipeline independently. [Phase isolation report](../experiments/merge-phases.md)

The runtime experiments show how much scope matters:

- **Fixed-width copy.** A guarded 16/32/64-byte specialization made short copies cheaper. Inlining it reduced alternating merge from 8.07 to 4.94 ms and its full pipeline from 12.79 to 9.80 ms, against Rust at 2.56 and 7.72 ms. The 4 KiB control used the generic path. Many small copies still paid a guard each. [Fixed-copy report](../experiments/fixed-copy.md)
- **Scoped fill.** A separate C lowering created a fresh buffer, filled it for the whole loop, and returned only the initialized prefix. The best variant per workload was within 8% of, or faster than, the fastest tested Rust control on the measured packed kernels and pipelines. This identifies a path for standard Lean toolchain work. The speed comes from the experimental lowering, with ABI and native implementation assumptions beyond the stock builder's source proof. [Scoped runtime report](../experiments/scoped-builder.md)
- **Wide accessors.** The actual Lean PR #14053 build reduced the preallocated v3 owned-row encoder from 14.65 to 4.13 ms at one million rows. The Rust control took 2.54 ms with its contiguous input layout. For alternating packed replay, the draft accessors took 3.47 ms and the fixed-size `memcpy` backport took 2.09 ms, compared with 5.88 ms for stock row copies. The post-store ownership assumption removed some static copy-on-write branches. Timing gains from the assumption varied with the loop. [Wide-accessor ablation](../../benchmarks/results/packed/wide-accessors)

For fresh encoding with a known row count, index an initialized destination using a machine-sized cursor. The v3 encoder using a prebuilt list improved by 3.36–3.71× over append. A `for` loop carrying a mutable cursor and buffer can allocate a boxed pair per row. Passing the `USize` cursor and buffer as separate tail-recursive arguments kept the cursor scalar in the owned wide-accessor encoder. For already packed inputs, preserve contiguous spans where they help and include the cost of an exact-size prepass in the full comparison. [Stock cursor](../../benchmarks/results/packed/stock-v3-cursor) · [V3 writer comparison](../../benchmarks/results/packed/v3-writer-comparison)

The tested nightly and PR toolchain retained the generic `copySlice` calls on the unchanged replay code. Compare a toolchain upgrade with unchanged sources, then measure code that calls its new primitives. For scope-wide writes, the v3 lowering gives a control for what can be achieved by allocating once and publishing the initialized length at the end. [Toolchain comparison](../../benchmarks/results/packed/upstream-toolchains) · [V3 scoped lowering](../experiments/compaction.md#whole-loop-v3-writer) · [Proof boundaries](../verification-status.md)

## Reproduce before generalizing

- Match input format, result semantics, bytes produced, allocation and initialization, and timed scope in Lean and Rust. Include a layout-matched control, scalar and SIMD controls where relevant, and comparable bulk strategies where either language has one. Record whether results are looked up, streamed, newly allocated, or emitted from a prepared plan. Keep VM comparisons with their original cohort. [Benchmark method](benchmarks.md#method) · [Fixed-copy scopes](../experiments/fixed-copy.md)
- Check the same deterministic inputs with an independent oracle. Use exact bytes for writers and include edge cases such as empty inputs, duplicate-key precedence across runs, full-width keys, malformed extents, and the edges of span lookahead windows. Checksum folds are useful for consuming results in timed loops. A commutative checksum can miss reordering. [Fixture generator](../../fixtures/generate.py) · [Fused fixture checks](../../benchmarks/fused_merge.py#L37)
- Run native release code. Inspect generated Lean C and the hot assembly for allocation, reference counting, bounds branches, generic calls, wide loads/stores and SIMD. Test a scalar control or simpler loop to isolate a code-generation change. The first generic replay experiment retained a Lean indirect call and moved Rust vector state through a callback. The reported comparison replaced those with direct loops. [Native code generation](../experiments/native-experiments.md#simd-scan) · [Replay controls](../experiments/merge-phases.md)
- Prevent timed pure results from being reused. The validation runner reads input through an `IO.Ref` each iteration, and the harness consumes the outputs. The exploratory validation timing without the reference was discarded. Pin CPU affinity, retain the deterministic seed and warm-up count, and save the trial rows and toolchain/environment details. Report per-query times as batch averages and Linux `VmHWM` as process peak RSS.
