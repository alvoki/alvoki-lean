# Reclamation contract

| Obligation | Completion condition |
|---|---|
| Publish before deleting | Every selectable manifest has intact run bytes and a complete WAL suffix. Durably publish replacement runs, directory entries and the manifest before deleting predecessors. Include generations held by readers and backups. Connect complete enumeration, stable holds and no-follow inode identity to the actual unlink and directory barrier, including partial effects. |
| Delete only covered WAL | Every recoverable checkpoint has the exact durable runs covering a candidate seal’s last sequence. Keep the active segment and every segment needed for replay. After any deletion prefix, crash, or failed barrier, preserve recovery and supported reads. Repeated collection from the actual remaining namespace must also work when the retry has an empty plan. Carry durable absence through arbitrary subsequent calls for both WAL and runs. |
| Reclaim row versions | Preserve point and range reads at every supported sequence, including a reacquired active snapshot. Keep all versions above the floor plus at most one floor anchor per key per run. A boundary tombstone counts. Further tombstone removal needs context from the memtable and every remaining run so an older value cannot reappear. Compose interrupted retention, checkpoint and both collectors through reopen. |
| Bound named space and prove progress | At a fixed floor the rewritten payload is bounded by 16 bytes per run plus 32 per above-floor row or floor anchor. A successful caller-scheduled pass with an empty memtable can publish those bytes. Bound additional retained names, cross-run duplication, active segment width, uncheckpointed frames (including uncertain submissions), metadata, staging peaks and maintenance backlog. With capped segment width and completed healthy collection, named WAL payload is bounded by uncheckpointed history plus one segment. An empty seal can still consume a name. Enforce the budgets in the policy. Show that each permanently eligible item is eventually reclaimed given successful I/O, available resources and continued scheduling. |
| Bound physical space | Named payload, unlinked but open inodes, and allocated blocks have different lifetimes. A block-release proof needs complete link and reference accounting across close, exec, exit and newly added aliases, an eviction condition, and a model of exclusive and shared blocks. Bound temporary peak allocation and specify the pool covered before claiming filesystem-wide free space. |

The existing complete maintenance and block-release proofs identify which of these conditions can already be consumed at a successful cut.
