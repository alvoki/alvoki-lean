# What it took to connect native L0 to its client contract

This is an implementation retrospective for the read, mutation and flush milestones. The [review inventory](l0-native-review.md) gives the producer graph. The [acceptance boundary](l0-native-acceptance.md) identifies the quantifiers and external assumptions. An independent reviewer can start from the public theorems in those two documents before reading this account.

## The problem that survived every change of proof architecture

Consider a put that filled the last slot of a WAL segment. The next delete rotates to another segment. After the worker succeeds, the final unlock fails. A client sees an error, the database has advanced, and the next successful get must observe the tombstone. To prove this, a model needs the old handle to stop being usable as the active writer, the newly installed child to own the right cursor, and the reported failure to retain the world in which the store really closed. Knowing the logical value of the delete is insufficient at each of these boundaries.

Flush creates a different ambiguity. A table can be complete and synced but unreachable from the active manifest. After an effective rename and before a successful directory barrier, the live namespace and the possible reboot namespaces give different answers. An old manifest and an orphan table are consistent. A new manifest referencing a missing table cannot justify a successful recovered read. Proving which bytes the writer emitted solves one part. Showing that the manifest selects a durable name for *that inode*, at the moment the reader needs it, solves another. These obligations arise from the storage semantics. No Lean tactic removes them.

A comparatively cheap step, once those identities were available, was getting back to client semantics. The read proof already knew how to consume a selected manifest, recoverable WAL and represented catalog. The public flush consumer builds that input on the actual reached files. Replay agreement and the existing trace theorem then do the work for both survivors. A surprisingly expensive step was cleanup. A mutex unlock when a child was already closed is still an issued operation. An error in the primary action can mask a later cleanup error in the public reply while both leave physical effects. Erasing either distinction makes it impossible to answer a later opener's question about the reached resources. [Flush consumer](../../lean/Alvoki/Experiments/L0/NativeFlushPublic.lean) · [Exit schedule](../../lean/Alvoki/Experiments/L0/ExitSchedule.lean)

## Three experiments that changed the boundary

**First, compose a read with another read.** The research checkpoint at `876256a6` replaced an interpretation of the entire get callback with framed file and read postconditions. The discriminating experiment was to catch a read failure and run get again. A theorem about the value returned on success has nothing to pass to the exception handler. A framed failure on the actual world gives that handler the resources for the second call. Milestone 1 at `b21dec18` moved the start of that argument back through concrete recovery and phase publication. This also exposed a separate issue. Preservation of WAL and table state does not prove that the transient root descriptor was dropped. The public success and failure outcomes now consume the acquired descriptor's lifetime contract, including tryLock, recovery and unlock errors. [Research checkpoint](https://github.com/alvoki/alvoki-lean/tree/876256a6005d0845519b15aada3b224275dbf3db) · [Public read and failure consumers](../../lean/Alvoki/Experiments/L0/WithOpenReads.lean)

**Second, spend the authority a producer returns.** Early receipts could describe a WAL execution and its allowed history. They did not themselves install the writer in the phase reference used by the caller. An extra correspondence premise could silently do all the interesting work. The replacement starts from the registered child, follows its actual phase and cursor through append or rotation, and returns an active registration in the resulting world. On an uncertain return the exact pending request survives close. The first successful recovery resolves the selection. The second open is constrained by the selection the first actually made. The old receipts were removed at `d1581e4a`. The stronger substitution test was a second public mutation on the same handle, followed by get. A different heap or freshly chosen child memory at the midpoint would make that a weaker test. [Public sequence](../../lean/Alvoki/Experiments/L0/MutationSequenceRoot.lean) · [Receipt removal](https://github.com/alvoki/alvoki-lean/commit/d1581e4a)

**Third, ask the recovered reader to find the output.** The old native bridge could relate a separate writer run to an installation map. Two executions returning equal row lists do not identify the writer descriptor in either execution. The replacement follows the installed memtable into a cursor over its rows, the exclusive writer into the file sync, and its live name into directory sync. The publisher frames that table as it changes the manifest. After reopen a fresh descriptor reads the same inode and bytes. The final positive witness initially still required the caller to provide a recoverable child at a later point in WAL opening. Reading actual CONTROL bytes, applying the existing store validation frames and consuming the result at the policy read removed that premise at `dea265d8`. This last change is a good example of reviewing *positive* proofs for hidden correspondence assumptions. [Writer](../../lean/Alvoki/Experiments/L0/NativeTableWriter.lean) · [Healthy recovered read](../../lean/Alvoki/Experiments/L0/HealthyFlushRead.lean) · [Removal of the whole-callback bridge](https://github.com/alvoki/alvoki-lean/commit/d8b83a0d)

## Where the lines went

**Measured.** On the pre-integration milestone 3 tree, `git diff --numstat a375c871 335bbff0` assigns 14,265 insertions to the L0 directory, 9,652 to WAL, 523 to SSTable and 767 to the rest. These are Git line counts by path, including tests and guides in those directories. They measure review surface. They do not estimate the minimum size of a proof. In particular much of the WAL increase constructs reusable native acquisition, rotation and crash producers for the first time. The old bridge and synthetic consumers removed at the end accounted for 1,358 lines of Lean across their files. The total net diff against main hides such replacements.

**My assessment.** Three kinds of cost recur.

| Obligation | Evidence from this implementation | What I would change on a second implementation |
| --- | --- | --- |
| Ordering and identity | A synced file, its synced directory name and the surviving manifest have different producers. An error may follow the effect. | Keep explicit transitions and distinct postconditions. A generic “durable output” would hide which barrier establishes which fact. |
| Transport | The same protected WAL, catalog or child registration moves through repeated binds, exception conversions and frame projections. Scan and publication preserve different subresources. | Reuse small rules for lifting an unchanged field across a concrete bind. Require two real consumers before adding a larger resource abstraction. |
| Return versus interruption | NativePost reasons through returned worlds. A nonreturning cut does not supply a return value to the continuation. Previously enumerated stops missed later read-to-EOF iterations and an already-closed unlock. | Share the effectful recipe with the observer from the first implementation. Prove erasure and reverse coverage when introducing the loop, before doing a case analysis of its crash outcomes. |

NativePost.Returns and IOReturns earned their cost. They carry the world through the two error channels of ExceptT over IO and compose at bind. ReadPost earned a separate interface because the reader needs a caller-selected frame even when a read fails. Positive reads need successful reports on *advancing* worlds. Sharing the reader induction avoids proving the parser again for those reports. ObservedIO serves a third purpose. A successful bind advances to its continuation with the actual result. A cut in the first action has no such continuation. Trying to express this with a bigger returned-error type would let a catch or finalizer run after process death. Conversely, an arbitrary cut relation can be empty while ordinary erasure still holds. Review both the construction at the leaves and the reverse theorem. [NativePost](../../lean/Alvoki/Experiments/WAL/Proofs/NativePost.lean) · [Reader induction](../../lean/Alvoki/Experiments/SSTable/Proofs/UnifiedReaderRelation.lean) · [ObservedIO](../../lean/Alvoki/Experiments/L0/ObservedIO.lean)

**Prediction.** The row-stream induction, fallible cursor and public read continuation should scale across more input formats and table layouts. Physical frame proofs tied to concrete nested records and phase swaps will scale poorly with additional independent owners. A useful trial would measure the number of changed consumer proofs when adding one protected file and the number of places that name a primitive when inserting one harmless read. Those measurements would justify, or argue against, a small frame-transport tactic. There is no measured percentage of the present diff that automation could eliminate.

## When the two branches met

The tested milestone 2 migration at `a622e1bd` kept the then-current framed reader and added the fallible cursor proof. Copying its file onto milestone 3 would have lost the newer shared reader induction. At integration there were two real conflicts. For the reader we put leaf/data simulation in the shared reader relation, used it for lookup and cursor, and retained the scoped public cursor theorem. For the writer we instantiated the existing builder induction at PR #33’s arbitrary state, error type and state projection. The same induction now underlies the L0 writer and the fallible sorted-run consumer. A successful writer test alone would have missed loss of input-error propagation. The joint check exercises that error theorem as well as healthy L0 reads. All WAL and L0 source blobs match the milestone 3 parent. The sorted-run implementation and its own tests match the main parent. [Integrated code tree](https://github.com/alvoki/alvoki-lean/tree/225a28e6c1812570095a63a5d2a41e86a5f062ef)

## Working in Lean against executable IO

* Write the consuming theorem first, with the incoming world, named reference or descriptor, returned value and outgoing world visible. Check the failure branch as a consumer too. A universally quantified “runtime law” about the whole callback is a sign to inspect the producer. A primitive law about a specific issued pread, offset and descriptor can be checked against the adapter.
* Use an equation such as `cases ran : a w` at the first effect whose outcome changes control flow. Rewrite the postcondition with `rw [Returns, ran]` where its shape permits it. Keep the resulting world named for the next call. Use `change` and `simp only` near an adapter between IO, BaseIO and ExceptT. Unfolding a large nested do-block throughout a proof couples it to details such as generated monad instances. The small lift and bind lemmas keep most callers away from those details.
* Induct on the object that generates the schedule. For a dependent continuation, generalize the starting world before induction. In `Program.classifyIf`, a later cut is reached using the actual value and state of the previous primitive. A list of operation names would lose the operand, for example the next chunk or the registered child after rotation.
* Distinguish a representation equality from an ownership fact. Equal serialized bytes can help prove replay or lookup. They cannot entitle the consumer to close a descriptor or to treat a different hard link as a fresh file. Keep the handle, inode, phase reference and registration named until the last operation that uses them.
* Place pure streaming reasoning at the point where the builder requests a row. The writer relation needs a source step, a sink append and a flush rule. It can share induction over packet emission and leaf flushing with a different world interpretation. Exact EOF and propagation of input errors are valuable separate contracts for a fallible sorted-run producer. [Builder relation](../../lean/Alvoki/Experiments/SSTable/Proofs/BuilderRelation.lean) · [Sorted-run consumer](../../lean/Alvoki/Experiments/SortedRun/NativeRefinement.lean)

The portable technique here is to return a resource in a form the next API actually accepts. That applies equally to parsers sharing a cursor or a transaction manager handing out a lease. The Lean-specific cost is repeatedly transporting dependent propositions along equalities of reached records. A small audited library for common conversions and a diagnostic that prints the final theorem's *semantic premises* would help. An axiom audit already checks kernel dependencies. It cannot tell whether the caller was asked to assume a whole-operation correspondence. A useful diagnostic would expand the fields of the runtime structures and list the operation at which each one is consumed. This is a tooling proposal, not a check that currently exists.

## Executable design and the next review

The most productive executable changes gave two callers one recipe. Flush exposes the bind from table creation to manifest publication. Phase update, close and finalization similarly expose their order. Interpreting that recipe as IO produces the existing runtime behavior. Interpreting it with observations identifies the interruption positions. Making an adapter or a theorem visible to the proof can be cheaper than changing the runtime data representation. Keeping verification history in executable handles would create a second source of truth and change runtime costs. [Flush bind change](https://github.com/alvoki/alvoki-lean/commit/0b7ca19e) · [Cleanup recipe change](https://github.com/alvoki/alvoki-lean/commit/316b7cd4)

One instructive integration test was a *source* change. Adding a second rename to the DurableBlob publisher broke correspondence at the manifest proof. A change to the returned database value alone might still pass black-box tests that only reopen the final files. For future components, try a mutation that preserves successful results but changes an intermediate persistent effect. Also exercise an actual reported error after a state change. The two tests challenge different assumptions. The PR #33 mutation suite contains three more reproducible examples, covering equal-key precedence, premature EOF and masking a writer input error. [Negative controls](../../scripts/check-sorted-run-mutations.sh)

If I were handing out the original task again, I would ask for four artifacts before expanding the proof to more cases.

1. A two-operation client that forces the first operation to produce a resource for the second. Include a meaningful failure continuation. Write down which identities the client needs to keep.
2. A premise ledger for that theorem. For every field ask for its executable producer or name the primitive and its external owner. Try to construct a model in which every system call fails. If the “successful example” still goes through, inspect its quantifiers.
3. A source-to-cut walkthrough for a loop, an error handler and a finalizer. Check the second iteration and the path on which cleanup itself fails. Ask whether a proposed cut can occur *before* its operand exists.
4. An exact commit with a cold dependency build, kernel replay, axiom audit and at least one deliberately wrong producer rejected. Keep the runnable fault fixture and the assumptions document beside the relevant component. Record which state the fixture actually destroyed.

Examples of how to lift a local rule and how to consume a returned child belong near the Lean producer. Filesystem failure semantics belong in a versioned contract. A reproducible negative control belongs in tooling. A skill could help navigate these checks once they recur across components. The number of phases, whether to expose a recipe as a small datatype, and whether to extract a prerequisite PR are local decisions. The experiments do not support making them universal policy.

## What I would do next

These are recommendations and open hypotheses. The integrated sorted-run merge supplies a verified streaming component. A database that selects compaction inputs, installs the output and reclaims old files still has additional obligations.

| Direction | First experiment or reusable boundary | What could invalidate the design |
| --- | --- | --- |
| Compact WAL and streaming recovery | Consume the same selected CONTROL and marker facts with a bounded decoder. Show that two legal chunkings yield the same replay suffix, including an incomplete final record. Feed the existing ready authority before changing the public write interface. | A byte-position checkpoint that forgets batch boundaries or the durable prefix can acknowledge an unrepeatable history after a torn tail. Space bounds need separate evidence from logical equivalence. |
| Recursive SSTable indexes and block iterators | Develop a pure navigation and termination proof independently. Reuse the fallible cursor contract for a descent across two levels, including a read error after yielding a row. | Recursive handles may retain a parent block or descriptor longer than the flat reader. Correct sorted rows alone do not bound memory or descriptor lifetime. |
| Compaction and reclamation | First publish the PR #33 output through the existing durable-file and manifest boundary. Keep deletion as a later operation whose producer proves the inode is unreachable from every permitted survivor and reader. | Newest-wins within two inputs need not justify dropping a tombstone when older runs remain. An old manifest, in-flight cursor or snapshot may still reference an apparently obsolete file. |
| Snapshots | Specify a pinned manifest generation, read view and release before building a collector. Test an old reader through publication of a new manifest. | Durable reachability and live reader reachability are different. Reusing a name can confuse a stale reader even if the current manifest is valid. |
| Concurrent and background work | Model one writer and one pinned reader first. Identify the publication point and the transfer of ownership of each file. Derive frames from those permissions. | Today's exclusive directory assumption is strong. An arbitrary scheduler can invalidate check-then-open, phase ownership and “last reference” claims. Fair scheduling is an additional progress premise. |
| Group commit | Track submitted, durable and replied batch frontiers. Lose an acknowledgement between two replies from the same completed barrier and reopen twice. | A single pending mutation cannot describe a partially acknowledged group. Treating receipt order as durable order can allow impossible histories. |
| Cloud-native storage | Prototype a separate publication contract for immutable object writes and conditional manifest replacement, with explicit read/list consistency and retry identity. Reuse pure formats and client histories first. | POSIX rename, directory fsync, descriptor lifetime and listing visibility do not translate directly. A timed-out conditional write may already have won. A retry must establish which generation won. |

I would prioritize the small experiments that multiple features consume: a pinned generation with an explicit lifetime, a streaming iterator that preserves both its error and its position, and a recipe whose returned and interrupted interpretations can be reviewed together. Pure format and index work can proceed independently. Reclamation needs a snapshot/reader lifetime design. Group commit needs a client history for multiple unresolved requests. Broad concurrency should wait until the component frames say who is allowed to mutate each resource. These dependencies are an engineering judgment. None of the roadmap rows is part of the current acceptance claim.
