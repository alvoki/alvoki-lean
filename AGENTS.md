## Designing a verified component

Use these steps when adding a component or changing a shared guarantee. Keep the design beside the existing contract or in its module guide. A short change can address the relevant questions in the review itself.

1. **Start at the caller.** Pick one observable behavior the next layer needs. Work backwards to components with distinct responsibilities. For each boundary, name the logical state, the operations and their outcomes, the assumptions supplied by the layer below, and the responsibilities left to the caller. Validate each new abstraction early with a concrete consumer and name the executable producer of each guarantee.
2. **Challenge the contract before depending on it.** Sketch the caller’s argument using only the proposed interface. Try substituting another implementation that satisfies the contract. Consumers and their correctness proofs should need no substantive changes. Try one behavior the contract must exclude and one it must allow. For a WAL, lose the append reply around the durability boundary, then reopen twice. The first successful open must return the history selected by the surviving state. A second open with no intervening operation must return that same history. Check that a healthy open can actually succeed. If the caller still needs marker slots to explain the result, or the fault model excludes the example by assuming recovery is correct, revise the boundary before building on it. Get an independent review of each substantial new or revised contract before investing in implementation and proofs.
3. **Prove one path through the real code.** Name the consuming theorem and derive its premises from local effects on the exact state or handle it receives. Prefer shared executable schedules down to meaningful primitives. Simplify executable code before adding correspondence relations. A conditional premise stays open until its producer proves it. Try a materially different failure or continuation against the same invariant. [Proof architecture](docs/proof-architecture.md#a-useful-proof-path) · [Proof techniques](docs/proof-architecture.md#lean-techniques-that-still-apply)
4. **Review what the extension cost.** If adding one failure repeats recovery proofs, a signature draws premises from several layers, or a public contract grows while caller behavior stays the same, inspect the boundary before adding cases. When proof complexity grows sharply, ask whether a simpler algorithm or representation could deliver the same public guarantee. Identify the distinction the caller can observe. Keep it where it matters, or prove a shared invariant at its producer and reuse the continuation. Migrate consumers and remove superseded paths. In the review, name the guarantee gained, the assumption discharged or added, and the reasoning reused or still necessarily separate.

When separating implementation from proofs, start at a public operation and follow its imports. Keep the evidence needed to construct a valid return value close to its constructor. Place theorems relating that value to the abstract model with their proof consumers. After migrating callers, compare the public operation’s transitive imports before and after, and check that its end-to-end theorem remains audited.

For a storage operation, describe the caller-visible invariant at its entry point. Use a short module guide when a reader needs to cross from the operation to its contract, tests and proofs. Link to the document that owns a guarantee or open obligation so a change has one place to update.

Keep documentation progressively navigable: introduce the concept and link to focused technical details. Keep overview documents roughly stable in size, avoid duplicating explanations, and use diagrams when they clarify a relationship or sequence. Keep historical progress primarily in Git rather than accumulating a running narrative in current guides.

## Agent work and review

- One agent can carry a component from design through proof. Give a changing boundary one owner. Parallelize independent producers or consumers once their interface is stable. Prioritize the end-to-end crash refinement recorded in `docs/progress.md`.
- Pin independent Lean readability reviews to a commit and a concrete task or set of files. Favor straightforward code that makes mistakes harder. Introduce an abstraction only when it simplifies the code, and use comments to explain subtle reasons and invariants.
- For concurrent write tasks, give each one its own worktree and branch so its candidate can be reviewed independently.
- At integration, obtain an independent review of the exact candidate diff. The integrating agent addresses findings and verifies the resulting candidate. Use focused module, kernel and axiom checks during iteration. Audit premises alongside axioms: identify who proves each premise and justify the remaining external assumptions. Where practical, compile a producer-to-consumer example to check this connection. Run the applicable integration checks on the reviewed candidate before pushing. For a prose-only change, check its claims, links and the identity of the verified code. When several agents collaborate, designate one to push integrated milestones.
- After each push, the coordinator sends the new `main` commit to the active agents. Agents working on dependent changes rebase their task branches and rerun the affected checks before returning their candidates.
