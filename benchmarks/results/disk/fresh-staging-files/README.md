# Fresh staging file measurements

The baseline is `f26d283`. The randomized candidate was built from `3f9c471`. The earlier alternating samples used `d0f5615` with the same staging implementation. The integrated `DiskTable` generates the same C as the randomized candidate. [Integrated source](https://github.com/alvoki/alvoki-lean/tree/ee6685e86f171db968403588f3f5709b3ac9b182) Both builds use the pinned Lean 4.36.0 release toolchain on the same VM. The first randomized cohort measured higher write latency. The difference was within the CPU 0 same-build interval and did not recur at that magnitude on CPU 4. The earlier alternating CPU 0 cohort measured 0.994× write, 0.987× aligned reopen and 0.979× torn-tail repair over nine pairs. Syscall traces of both two-write builds counted six stage write opens, six stage renames and zero stage unlinks, including bootstrap and warmup. The candidate's stage opens add `O_EXCL`. Build `alvoki-disk-write` and `alvoki-disk-replay` with `lake build` from each revision's `lean` directory. Use `taskset -c 0` or `taskset -c 4` for each executable invocation. A write invocation uses `alvoki-disk-write 40 2`. Each raw write sample reports the elapsed nanoseconds for 40 individual acknowledged writes. Divide by 40 to obtain the per-write values above.

For replay use `alvoki-disk-replay DIR 2048 2` with a fresh fixture for each invocation. Use a flat `WAL` with 2,048 ascending frames and a `WAL.commit` marker for those bytes, generated by the independent Python encoder. Both historical builds use the flat layout. For torn-tail repair append the 11-byte tail after encoding the marker and pass `--repair-tail`. Each raw replay sample measures one open. The first native trial in each invocation warms the executable and validates the table. [Fixture generator](../../../disk_replay.py) · [Write benchmark](../../../../lean/DiskWriteBench.lean) · [Reopen benchmark](../../../../lean/DiskReplayBench.lean) · [Current segmented WAL measurements](../native-segmented-wal)

The randomized comparison uses 12 pairs on CPU 0. The follow-up uses 12 same-build pairs on CPU 0 and 16 candidate pairs interleaved with 16 same-build pairs on CPU 4. Each pair has two timed samples per side. Within each cohort, each build goes first in half the pairs, balanced in a seeded shuffle. The raw `sequence` column records the execution order within a pair. The ratio divides the comparison median by the baseline median over the pooled samples. The intervals use 3,000 bootstrap draws of whole pairs. Seeds are 20261124 and 20261125 for the two shuffles and the corresponding seed plus one for each bootstrap.
